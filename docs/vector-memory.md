# Векторная память Hayumeri — первая рабочая основа

Hayumeri получила **серверный модуль Qdrant** `server/src/vector-memory.ts`. Он не заменяет документы и чаты — он хранит индекс их векторов, чтобы в будущем находить относящиеся к вопросу фрагменты.

## Что уже работает

- Создание отдельной коллекции для **конкретной модели эмбеддингов и размерности**. Это исключает случайное смешивание несовместимых векторов.
- Сохранение подготовленных векторов с идентификатором пространства, документа, фрагмента, ревизии, хешем исходного документа, типом и временем.
- Запрос похожих векторов с оценкой сходства, ограничением результата и фильтром пространства/источника.
- Повторная запись того же фрагмента обновляет запись с тем же ID вместо создания дубликата.
- Точное удаление всех векторов конкретного источника в конкретном пространстве. Исходный документ **не удаляется**.
- Векторы, HNSW-индекс и payload создаются **на диске** для экономии оперативной памяти Qdrant. Могут использоваться дополнительные RAM и место на SSD.
- Нет искусственного глобального лимита на число векторов. Записи отправляются порциями по 64; размер одного запроса и результата ограничивается для безопасности.
- Недопустимые данные (NaN/Infinity, нулевые векторы, неподходящая размерность, некорректные идентификаторы) отклоняются до записи.

## Важное ограничение: эмбеддинги

**Преобразование текста в векторы пока не подключено.** Qdrant хранит векторы и находит близкие, но сам не понимает обычный русский текст без настоящей модели эмбеддингов. Новый модуль принимает **готовые числовые векторы от совместимой модели**. Он специально не имитирует смысловой поиск поиском совпадающих слов и не отправляет документы в облако без настроенного провайдера.

Для полноценной автоматизации далее нужны модель эмбеддингов (локальная или Cloud.ru), согласование размерности, очередь индексирования заметок/документов, обнаружение изменений и удалений, а также вызов поиска перед ответом ИИ. До этого момента раздел «Память» не должен показывать вымышленные найденные факты.

## Проверки

GitHub Actions на Linux поднимает настоящую Qdrant в Docker и выполняет `npm --prefix server run memory:smoke`. Тест использует **отдельную временную коллекцию**, проверяет запись, поиск, порядок результатов, изоляцию двух пространств, обновление ревизии и удаление только своего источника. В конце временная коллекция удаляется; пользовательские коллекции не затрагиваются.

Переменные доступа загружаются из локального `.env.nosql` на сервере, не из браузера. Коллекции находятся в именованном томе Qdrant из `docker-compose.nosql.yml`. Том не входит в GitHub-обновления. Перед переносом Windows или сменой SSD необходим отдельный бэкап Docker-данных, а не только папки проекта.

## Предусмотренный API TypeScript

```ts
import { VectorMemory } from './vector-memory.ts';
import { loadSettings, vectorClient } from './databases.ts';

const memory = new VectorMemory(vectorClient(loadSettings()), {
  modelId: 'embedding-model-v1',
  dimension: 768 // Должна совпадать с фактическим выходом модели
});

// Позже агент передаст сюда эмбеддинги, реально полученные от модели.
// memory.remember(chunks)
// memory.recall({ namespace: 'personal', vector: queryEmbedding })
// memory.forgetSource('personal', sourceId)
```

Векторная память — инструмент **поиска**, а не источник доказанной истины. Для ответов ассистент должен прочитать исходный документ по `sourceId` и проверить факты, дату и применимость найденного фрагмента.
